# Personal Finance ETL — v9.2.0 Implementation Hardening Plan

> **Theme:** Make the implementation simpler to reason about and cheaper to execute.  
> **Prerequisite:** v9.1.0 contracts and documentation are frozen.  
> **Scope:** workflow complexity, cyclomatic complexity, nesting, Polars execution boundaries, intermediate state, and measured performance.  
> **Out of scope:** contract redesign, finance features, ML/AI, and financial-semantic changes.

## Release objective

```text
v9.1.0
What does this code mean?
        ↓
v9.2.0
How cleanly and efficiently
is that meaning implemented?
```

Baseline: 56 public functions >80 lines; 27 >150; ~70 functions with estimated CC >=10; 17 >=20; 10 >=30; 32 functions nesting >=4; 76 Polars materialization/conversion calls across 29 files.

# Phase 1 — Complexity baseline and exceptions

Classify hotspots as:

```text
DECOMPOSE
SIMPLIFY_BRANCHING
EXTRACT_POLICY
EXTRACT_TYPED_OPERATION
KEEP_COHESIVE
NUMERICAL_KERNEL_EXCEPTION
DECLARATIVE_EXCEPTION
STATEFUL_ALGORITHM_EXCEPTION
```

Protect legitimate exceptions, especially the Numba Monte Carlo kernel.

**Exit:** every major hotspot has an intended treatment before code changes.

# Phase 2 — Quant workflow decomposition

Primary target: `IsinProcessor.process()` (~655 lines, estimated CC ~129).

By release end it should read primarily as application sequencing over frozen v9.1 contracts.

Look for cohesive operations: prepare context → build lots → valuation → reconciliation → performance → result.

Secondary targets: `IsinPipeline.process_all()`, `AggregationService.run()`, `SnapshotGenerator.generate()`, and realized/performance workflows.

Do not create dozens of tiny forwarding methods.

**Exit:** Quant orchestration is readable at a glance with identical financial outputs.

# Phase 3 — Other complexity hotspots

Review NetWorth/FIRE/household builders, Tax classification/event normalization, file synchronization, restore/recovery, warehouse healing, and pipeline failure handling.

Use guard clauses, named decisions, policy/lookup tables, typed intermediate results, cohesive helpers, and pattern matching where clearer.

Prioritize cognitive complexity, not line count.

**Exit:** high-value CC/nesting hotspots are materially easier to trace.

# Phase 4 — Polars materialization audit

Classify every meaningful `collect`, `collect_schema`, `to_dicts`, `rows`, and `iter_rows` as:

```text
PUBLICATION_BOUNDARY
STATEFUL_ALGORITHM_BOUNDARY
THIRD_PARTY_BOUNDARY
SCALAR_EXTRACTION
PROCESS_BOUNDARY
VALIDATION_DIAGNOSTIC
SCHEMA_INSPECTION
UNNECESSARY
```

Priority: investment market state → FX → input adapter → aggregation → ISIN service → provider/warehouse boundaries.

Only `UNNECESSARY` is an automatic removal target.

# Phase 5 — Lazy-plan and intermediate-state optimization

Remove proven unnecessary eager boundaries, Polars→Python→Polars round-trips, duplicate intermediate frames, repeated sorts/joins/casts/schema resolution, and redundant canonicalization.

Preserve stateful Python boundaries where correct, especially FIFO.

No optimization is accepted merely because it looks cleverer.

# Phase 6 — Benchmark and certification

Benchmark representative workloads with the same data/config/machine conditions.

Record end-to-end and major phase timings, Quant, Tax, Wealth/FIRE, and peak memory if practical.

Run mypy, Pyright, Ruff, architecture tests, regression tests, and full real pipeline.

## v9.2.0 Definition of Done

- highest-value giant workflows decomposed;
- major cyclomatic/nesting hotspots reduced or justified;
- every materialization boundary classified;
- unnecessary eager boundaries removed;
- no unexplained performance regression;
- financial outputs identical;
- v9.1 contracts stable;
- legitimate numerical/stateful complexity documented rather than cosmetically fragmented.

> **Outcome:** the implementation is as disciplined as the architecture surrounding it.
