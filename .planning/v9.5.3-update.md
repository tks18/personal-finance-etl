# Personal Finance ETL — v9.5.3 Code Quality Refactor Plan

## Purpose

v9.5.3 is a **behavior-preserving code-quality patch** before the multi-release Grand Refactor program.

The objective is to enter the future source-agnostic / Pre-Bronze / configurable-ingestion work with a cleaner and more modular baseline, without changing financial meaning, persistence semantics, observability behavior, configuration contracts, or user-facing behavior.

> **v9.5.3 rule:** improve how the current system is implemented, not what the current system does.

---

## Release-wide invariants

These invariants apply to every phase.

- Financial outputs must remain identical.
- Bronze, Silver, Gold, and Control Plane semantics must remain unchanged.
- Existing configuration contracts must remain compatible.
- Observability event semantics, correlation, lineage, and forensic behavior must remain unchanged.
- Multiprocessing behavior must remain unchanged.
- CLI/Desktop behavior must remain unchanged.
- No Pre-Bronze implementation.
- No Pandera integration.
- No configurable source-generalization work.
- No capability-planning architecture.
- No new financial features.
- No schema redesign solely for cleanliness.
- Performance must not materially regress.

After each meaningful phase, run the relevant focused tests. Run the complete quality gate before release.

# Phase 2 — Mega-Function Decomposition

## Goal

Reduce the highest-value function complexity without changing algorithms or financial semantics.

## Primary targets

### `presentation/docs/renderer.py`

`build_html_app` is exceptionally large.

Refactor toward focused rendering/component helpers while preserving generated output and presentation behavior.

### `domain/fire/deterministic.py`

Decompose `build` around natural responsibilities such as:

- input preparation;
- projections;
- milestone calculations;
- risk calculations;
- output assembly.

Do not change FIRE formulas.

### `domain/household/transforms/calendar.py`

Decompose `transform_d_calendar` into clear calendar construction, enrichment, and business-rule stages.

### `domain/household/budget.py`

Separate preparation, calculations, forecasting, and final output construction.

### `domain/household/income.py`

Separate normalization, aggregation, metric calculation, and output construction.

### `application/pipeline/transformer.py`

Break `run` into explicit transformation stages while retaining the same orchestration order and failure semantics.

### `domain/market/fx.py`

Separate validation, reconstruction, joins, and final projection where appropriate.

### `domain/market/benchmarks.py`

Separate validation/preparation, transformation, and projection responsibilities.

## Special non-goal

Do **not** mechanically split `domain/fire/simulation/kernel.py::_run_mc_simulations_numba`.

It is a numerical hot-path kernel. Refactor it only if there is a compelling structural reason and identical numerical output plus performance can be demonstrated.

## Expectation

Large functions become easier to reason about and test, but the public behavior and financial calculations remain identical.

## Exit gate

- [ ] High-priority mega-functions have clear responsibility boundaries.
- [ ] Extracted helpers have focused names and narrow contracts.
- [ ] No unnecessary classes were introduced.
- [ ] Financial regression remains exact.
- [ ] Relevant focused tests pass.
- [ ] Runtime does not materially regress.

# Phase 4 — ISIN and Investment Service SRP Cleanup

## Goal

Make investment multiprocessing orchestration easier to understand without disturbing its carefully established process and observability boundaries.

## Primary targets

- `application/investments/isin_service/pipeline.py`
- `application/investments/isin_service/worker.py`
- `application/investments/isin_service/metrics.py`
- `application/investments/quant_service.py`
- `application/investments/aggregation_service/pipeline.py`

## Work

Look for clean separations between:

1. task preparation;
2. worker-input construction;
3. multiprocessing execution;
4. worker-result interpretation;
5. structured failure construction;
6. result aggregation;
7. metrics/output assembly.

Preserve the current rule:

> Workers own computation; the parent process owns orchestration and observability.

Do not move the observability system into worker processes.

## Expectation

The ISIN pipeline becomes easier to test and maintain while preserving multiprocessing, deterministic financial behavior, and deep failure lineage.

## Exit gate

- [ ] Task preparation is separated from execution where useful.
- [ ] Worker-result interpretation is focused and testable.
- [ ] Failure construction remains single-event and traceback-complete.
- [ ] Parent-owned observability remains intact.
- [ ] Investment outputs are identical.
- [ ] Multiprocessing tests pass.
- [ ] Runtime does not materially regress.

# Phase 6 — Typing and Boundary Cleanup

## Goal

Remove accidental typing uncertainty while preserving justified dynamic boundaries.

## Primary review areas

- `infrastructure/observability/diagnostics.py`
- `infrastructure/providers/market/benchmark.py`
- `infrastructure/providers/market/common.py`
- `domain/fire/simulation/batch.py`
- `domain/fire/simulation/kernel.py`

## Work

Classify remaining `Any` usage as:

- accidental and removable;
- external-library boundary;
- dynamic provider payload;
- Numba/numerical boundary;
- intentionally heterogeneous diagnostic context.

Replace accidental `Any` with an existing or new narrow contract where that improves clarity.

Use:

- dataclasses for internal structured state;
- TypedDict for known dictionary shapes;
- Protocol for behavioral boundaries;
- Pydantic for validated runtime/configuration models;
- explicit aliases where they improve readability.

Do not introduce complex generic/type machinery merely to reach a numeric `Any = 0` target.

## Expectation

Uncertainty remains only where the system genuinely interfaces with dynamic external/runtime behavior.

## Exit gate

- [ ] Every remaining meaningful `Any` is justified.
- [ ] Accidental broad types are narrowed.
- [ ] Mypy passes.
- [ ] Pyright passes.
- [ ] Public interfaces remain understandable.
- [ ] No runtime behavior changed for typing purity.

# Phase 7 — Materialization, Duplication, and Dead-Code Audit

## Goal

Finish the cleanup by reviewing eager execution boundaries and removing genuinely redundant implementation residue.

## Part A — Polars materialization

The v9.5.2 baseline contains approximately 23 explicit `.collect()` calls.

Prioritize review of:

- `domain/investments/valuation/market_state.py`
- `domain/market/fx.py`
- `application/ingestion/market_sync.py`
- `application/investments/aggregation_service/pipeline.py`
- `application/pipeline/transformer.py`

Classify each collection as:

- **required materialization**;
- **justified architectural boundary**;
- **avoidable eager collection**.

Do not optimize solely to reduce the count.

## Part B — Duplication

Search for repeated:

- dataframe preparation;
- result conversion;
- provider handling;
- failure construction;
- schema projection;
- orchestration boilerplate.

Extract only stable concepts.

## Part C — Dead/redundant code

Review:

- unreachable helpers;
- obsolete compatibility paths;
- unused imports;
- stale constants;
- duplicate utilities;
- superseded comments/docstrings.

Do not remove code merely because static search shows few callers without verifying test and runtime reachability.

## Expectation

The codebase becomes leaner and clearer without turning performance cleanup into algorithm redesign.

## Exit gate

- [ ] All `.collect()` boundaries are reviewed.
- [ ] Avoidable eager collections are removed only where safe.
- [ ] Required collections remain explicit and understandable.
- [ ] Meaningful duplication is reduced.
- [ ] Dead code is removed only after reachability verification.
- [ ] Cached/cold runtime is equal or better within normal variance.
- [ ] Financial outputs remain identical.

# Explicitly Deferred to the Grand Refactor

Do **not** start these in v9.5.3:

- Pre-Bronze;
- source-agnostic ingestion;
- configurable source contracts;
- configurable hash/change-detection policies;
- configurable Bronze mappings;
- Pandera dataframe contracts;
- configurable deterministic identity generation;
- capability graph/planner;
- capability-aware Silver/Gold publication;
- execution-plan compilation;
- Config Studio;
- Analytics Studio;
- documentation-repository migration.

These belong to the dedicated multi-release architecture program after v9.5.3.

# Recommended Working Order

```text
Phase 1  Baseline
   ↓
Phase 2  Mega-functions
   ↓
Phase 3  Provider duplication
   ↓
Phase 4  ISIN / investment SRP
   ↓
Phase 5  Infrastructure modularity
   ↓
Phase 6  Typing
   ↓
Phase 7  Materialization + dead code
   ↓
Phase 8  Certification
```

Work one phase at a time. Keep commits small and behavior-preserving.

The purpose of v9.5.3 is not to make Personal Finance ETL theoretically perfect. It is to remove known structural friction so the Grand Refactor starts from a clean, modular, well-tested baseline rather than carrying avoidable code-quality debt into a much larger architectural transformation.
